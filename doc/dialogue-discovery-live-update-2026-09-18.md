# 推荐卡片不刷新回填修复（2026-09-18）

## 故障原因

音乐助手提交任务前已有当前会话 SSE 连接，但提交成功后前端仍会关闭并重连同一会话。SSE 网关在没有旧事件 ID 时从当前最新事件继续，重连间隙发布的 `session`/`done` 事件可能被跳过。发现任务的后台观察器只轮询约 30 秒，任务若更晚完成，就不会再推送卡片更新。前端此前没有持久任务或发现状态校对，因此数据库已有结果时，页面可能一直显示旧卡片，刷新才看到。

## 修复

- 同一会话复用现有 EventSource，不在每次发送后重建连接。
- 已接受的对话任务每 3 秒读取持久任务状态；SSE 丢失时自动拉取最新会话，消除“必须刷新页面”的依赖。
- 含待补候选的推荐卡每 2.5 秒检查发现任务。发现完成或失败后调用卡片刷新接口，并原位更新当前会话。页面重新打开待补卡片也会自动继续校对。
- 后端把 `needs_reconciliation` 视为终态失败，避免卡片永久显示“正在补充”。
- 120 秒提示只说明处理较久，继续等待持久任务；不再错误地把仍在运行的任务标成完成或失败。

## 验证

新增无 SSE 的真实浏览器回归：模拟持久任务完成、发现任务稍后完成，页面不刷新即可显示完整推荐卡；用真实后端旧数据中的一张“排队中但发现任务已完成”的卡片复测，页面未刷新即自动回填为 `completed`。后端回归覆盖观察器推送完整卡片和需要人工核对的终态。42 项定向测试与前端生产构建通过；AMEM、Radio、SSE 等容器重建后健康。

联调中曾遇到 Docker Desktop Windows 绑定目录的 SQLite `disk I/O error`。停止 Radio 服务后，两份数据库 `PRAGMA quick_check` 均为 `ok`；重启服务后连续健康检查恢复。后续检查运行中的数据库统一从容器内执行，避免 Windows 与 Linux 两侧同时直接打开同一绑定目录中的 SQLite 文件。生产环境迁移到 Linux 原生卷可进一步降低该类文件共享风险。
