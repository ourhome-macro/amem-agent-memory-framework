# Radio 资源、播放与推荐链路调整（2026-09-18）

## 实测与问题

- 运行中的旧版 MySQL、Redis、RocketMQ 容器来自已不存在的 `docker-compose.go.yml`，不属于当前 Radio 栈。清理前其中 MySQL 约 452 MiB、RocketMQ namesrv 约 369 MiB；已移除这些旧容器，保留具名数据卷。
- 当前 Radio 栈清理前合计约 1.2 GiB。Celery task/event worker、AMEM、后端与 RabbitMQ 是当前异步推荐、SSE 和记忆写入所需的服务，未直接删除。
- 本地同一曲目冷启动取流信息约 538ms，之后代理音频首字节约 311ms；旧前端串行等待取流信息再开始加载音频。进一步排查发现前端静态代理使用 `response.read()`，把整段音频缓冲完才送给浏览器，这是主要延迟来源。
- “唱跳舞台”原先不是 `RequestSpec` 硬约束；发现计划与向量重排会混入长期画像，可能返回与本轮要求无关的歌曲。

## 本轮改动

- 首页推荐列表只显示歌曲信息，不显示推荐理由；“今天我想陪你听”区域只保留状态输入框与保存按钮，移除画像标签、MBTI、人格叙述和理由面板。音乐助手页顶部也移除了近期听感标签。
- 没有个人 DeepSeek API Key 的账号不能提交音乐助手操作；顶部显示配置提醒。首页推荐继续使用已有行为、收藏与反馈构成的规则模式，跳过 LLM 调用。
- 会话列表增加按用户隔离的删除操作。删除会话前检查进行中的对话或发现任务；会话消息、卡片、信号与检查点随外键级联删除。
- 唱跳舞台请求成为本轮硬约束：发现查询先按舞台内容搜索，候选必须具有舞台与舞蹈证据；这一轮不使用稳定偏好得分或画像向量词补位。没有匹配候选时返回空结果并继续补充，不返回无关歌曲。
- 已知曲目播放先请求音频代理，再并行获取清晰度、时长等元数据；播放器在加载流后立即发起播放请求。前端代理对音频改为逐块转发，并保留 `Range`、`Content-Length` 与 `Content-Range`。首页与推荐卡片只预热前两首的取流信息。
- 首页收到首批推荐后立即结束加载状态；发现任务在后台完成后再更新推荐列表，不让页面等待最长 20 秒的补候选轮询。

## 部署与验证

本地 `AUTH_MODE=disabled` 时只有 `legacy-owner` 演示账号。正式多账号需要 OIDC；若要求每位用户自带密钥，应将生产 `DEEPSEEK_API_KEY` 留空。

## 验证结果

- 旧服务容器清理后，当前 Radio 容器采样合计约 0.9–1.2 GiB；相较清理前减少约 0.8 GiB。旧 MySQL、Redis、RocketMQ 的具名数据卷仍保留。
- 代理流测试验证：上游只发送首个 8 KiB 并暂停时，前端代理在上游结束前就将首块交给客户端。真实 B 站音频整段约 5.6 MiB，浏览器代理首块约 412ms，Edge 实测点击到 `playing` 约 738ms（单首样本）。不同 B 站源站与网络状态仍会影响结果。
- 后端用两个账号验证 API Key、会话和删除权限隔离；无个人 Key 时服务端拒绝助手写操作，规则推荐不会调用画像 LLM。
- 新场景测试验证“唱跳舞台”是硬约束，高分但无舞台内容的个人偏好歌曲被过滤；原有推荐、发现与工作流回归通过。合并定向测试 40 项通过。
- 桌面浏览器核对首页已移除推荐理由、画像标签、MBTI 和原因面板；无 Key 状态显示顶部通知与助手锁定入口。
- 真实浏览器完成新建会话、发送消息、接收 SSE 回复和删除测试会话，JavaScript 错误为 0；浏览器脚本会清理自己创建的会话。
